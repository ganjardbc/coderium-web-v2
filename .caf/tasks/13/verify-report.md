## Task 7 — Cross-check kontrak error publish (done via read-through, not live curl)
Read `apps/api/src/shared/filters/all-exceptions.filter.ts`: it spreads
`exception.getResponse()` (the object thrown by `assertPublishable` —
`{ message: 'Validasi publish gagal', fields: [...] }`) directly into the
top-level JSON response body, alongside `success`, `statusCode`, `timestamp`,
`path`, `message`. So the actual body is:
```json
{
  "fields": ["cover", "ctaUrl", "pipelineSteps", "features"],
  "success": false,
  "statusCode": 400,
  "timestamp": "...",
  "path": "/admin/products/:id/publish",
  "message": "Validasi publish gagal"
}
```
`fields` is top-level in `err.response.data`, matching the assumption in
`requirements.md` (`err.response.data.fields`) — no change to frontend parsing
was needed. This was **not** additionally verified via a live curl/Swagger call
(no running `apps/api` instance was started in this session); confirmed purely
by reading the exception filter + `assertPublishable` source, which is one of
the two verification methods explicitly allowed by tasks.md Task 7 ("...atau
baca ulang NestJS exception filter behavior"). If a human wants live
confirmation, run `apps/api` locally and hit
`POST /admin/products/:id/publish` on a draft product missing required fields.

   derived purely from which submit button is clicked ("Save & Publish" vs
   "Save as Draft"), consistent with the Planner's recommendation and with the
   `/publish` `/unpublish` `/archive` action-endpoint model. List page still
   handles publish/unpublish/archive/restore as separate row actions.

   section above) — `fields` top-level, as assumed.
3. `manage_products` permission confirmed present in seed — no blocker.

## Notes for reviewer / next agent
- `ProductForm.vue` mutates the `form` prop object's fields directly
  (`v-model="form.name"` etc.) rather than emitting `update:modelValue` for
  every keystroke, since `create.vue`/`edit.vue` pass the *same* reactive
  object down (not a copy) — this is intentional and mirrors how
  `RepeatableListField` still uses proper immutable emits for structural
  array changes (add/remove/reorder). No ESLint is configured in this
  package to flag this as a prop-mutation anti-pattern; flagged here for
  visibility in case the team later adds lint and wants this pattern
  reviewed/refactored to strict two-way emits.
- Slug auto-generation (`slugify` in `ProductForm.vue`) is a simple
  lowercase/strip-non-alnum implementation matching the requirement; the
  server (`apps/api` `slugify` from `@coderium/shared-utils`) remains the
  source of truth / re-generates when `slug` is sent empty.
- Not implemented (explicitly out of scope per tasks.md/requirements.md):
  drag-and-drop reordering in `RepeatableListField` (up/down buttons only,
  which tasks.md marks as sufficient — drag-drop "tidak wajib").
